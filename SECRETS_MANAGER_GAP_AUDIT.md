# DoctorHide vs AWS Secrets Manager — Gap Audit

## Verdict

DoctorHide is a well-built **zero-knowledge passphrase vault**, not an AWS Secrets Manager clone — and that distinction is the headline. It nails the cryptographic foundations of a secrets store (PBKDF2-HMAC-SHA256 at 600k iterations + Fernet encryption at rest, passphrase never persisted, API keys hashed and shown once, mandatory TOTP for humans, clean tenant isolation by construction), but it is missing nearly every *operational* capability that makes Secrets Manager a managed service: no versioning, no rotation, no audit trail, no fine-grained authorization/policies, no envelope encryption/KMS, no soft-delete/recovery, no tags, and a read-only programmatic API with no batch or write operations. **The single biggest blocker is the architectural tension at the core: the zero-knowledge design (server never holds the passphrase, decryption is client-side) is fundamentally incompatible with the server-driven features that define Secrets Manager — automatic rotation, managed DB-credential integrations, envelope encryption under a server-held CMK, and server-side decryption for GetSecretValue.** Reaching parity is not incremental hardening; it requires adding a parallel server-side-key (CMK/envelope) crypto model alongside (or instead of) the passphrase model.

## What it already does well

- **Real encryption at rest, no plaintext leakage.** PBKDF2-HMAC-SHA256 (length 32, 600k iterations, 16-byte per-project salt) derives a Fernet key; only ciphertext is stored. `vault/crypto.py:25-34` (derive_key), `:50-55` (encrypt/decrypt); `vault/models.py:53-68` (Secret stores only `ciphertext`).
- **Genuine zero-knowledge on the API path.** The passphrase is never persisted (only salt + iterations + verifier); the REST API returns ciphertext + KDF metadata so a leaked `dhk_` key still cannot decrypt without the out-of-band passphrase. `vault/api.py:12-20,34-47`; `vault/crypto.py:1-7`.
- **Passphrase-correctness check without storing the passphrase.** A Fernet-encrypted constant verifier validates a re-derived key. `vault/crypto.py:37-47`; `vault/views.py:100-104`.
- **Strong API-key hygiene.** Both key types (`dhk_`, `dh_live_`) store only SHA-256 of a 32-byte high-entropy secret + prefix + last_four; plaintext shown exactly once; constant-time `hmac.compare_digest` verify; expiry + revocation enforced at auth time. `vault/models.py:89-127`; `iam/models.py:66-108`.
- **Mandatory TOTP 2FA for humans, with replay protection and backup codes.** Password alone does not log in (pending-session gate); `match_token` blocks replay; 10 single-use static backup codes issued and downloadable as PDF. `accounts/views.py:82-94,147,206-222`.
- **Correct tenant isolation by construction.** The REST principal *is* the Project (`project = request.user`), with no project_id in the URL to tamper with, so cross-tenant access is structurally impossible. `vault/api.py:23-31`; `vault/api_urls.py:5-8`.
- **Pluggable custom user model + clean machine/human principal split.** `AUTH_USER_MODEL = 'accounts.User'`; `ServiceAccount`/`Project` act as DRF principals; `/whoami` distinguishes them. `settings.py:143`; `iam/views.py:7-14`.
- **Secret hygiene in config.** `.gitignore` excludes `.env`, keys, certs, logs; only DB config is env-driven. `.gitignore:3-15`; `settings.py:90-101`.
- **Meaningful crypto/auth test coverage.** Crypto round-trip, wrong-passphrase rejection, passphrase-not-stored, unauth 401, revoked-key 401, ciphertext-not-plaintext. `vault/tests.py:25-96`; `iam/tests.py:12-77`.

## Gap roadmap (impact-first)

- **Audit trail of every API call (CloudTrail-equivalent)** — *missing*. Why it matters: for a secrets manager, "who read/changed which secret, when, from where" is the system of record; reads must be auditable, not just mutations. Delta vs AWS: AWS records immutable append-only events (principal, action, secret ARN, timestamp, source IP, user-agent, outcome); DoctorHide logs nothing — the only signal is `APIKey.last_used_at`, a single mutable per-key timestamp with no action/resource/IP and absent for human reads (`vault/authentication.py:40-41`). Effort: **M**. Pointer: add an `AuditLog` model + write hooks in `vault/api.py` (secret_detail/secrets_list), `vault/views.py` (add/delete/reveal), and both `authentication.py` backends; configure `LOGGING` in `settings.py`.
- **Resource-based policies / fine-grained access control** — *missing*. Why it matters: real secrets managers grant a specific principal read-only access to one secret and deny everyone else; DoctorHide is all-or-nothing per project. Delta vs AWS: no policy/grant model, no scopes, no per-secret ACLs, no explicit-deny; `dhk_` keys are 1:1 with a project, `dh_live_` keys grant nothing beyond `/whoami`. (`vault/api.py:23-47` IsAuthenticated only; no `permissions.py` anywhere.) Effort: **L**. Pointer: add a Grant/Policy model on Secret/Project, a `vault/permissions.py` DRF permission class, and scoped API keys.
- **Identity-based authorization (principals × actions × conditions)** — *partial*. Why it matters: least-privilege requires a fine-grained action set and request-context conditions, not a single `IsAuthenticated` gate. Delta vs AWS: authentication/principals are solid, but there are no enumerated actions (read/list/write/delete/rotate), no attachable policies, no conditions (source IP, MFA-present, time, tags). (`settings.py:154-156`; `vault/api.py:23-47`.) Effort: **L**. Pointer: same `vault/permissions.py` layer + action enum on keys; depends on the policy model above.
- **Envelope encryption with KMS-style CMK + per-secret data keys** — *partial*. Why it matters: a central, independently-rotatable/disable-able master key plus per-secret DEKs limits blast radius and enables instant revocation. Delta vs AWS: DoctorHide is single-tier (one passphrase-derived key encrypts every secret in a project), AES-128 (Fernet) not AES-256-GCM, no DEK/KEK split, no wrapped-key column, no CMK/KMS. (`vault/crypto.py:25-55`; `Secret` has no wrapped-DEK column, `vault/models.py:53-68`.) Effort: **L**. Pointer: new server-side master key (env/KMS), add `wrapped_dek` column to Secret, rewrite `vault/crypto.py` to a two-tier model — **architecturally parallel to, not a refactor of, zero-knowledge**.
- **Customer-managed master keys / pluggable KMS + master-key rotation** — *missing*. Why it matters: externally-managed key material, key disable = instant revocation of all secrets, rotation independent of data. Delta vs AWS: no key hierarchy, no key-provider abstraction, no key id/ARN reference, no master-key rotation; even passphrase-change/re-encryption is unimplemented. Effort: **L**. Pointer: a `KeyProvider` interface (local/AWS-KMS/Vault) + key-id column on Project/Secret; builds on the envelope-encryption gap.
- **Secret versioning with staging labels (AWSCURRENT/AWSPENDING/AWSPREVIOUS)** — *missing*. Why it matters: versioning is the substrate for rotation, rollback, and safe atomic promotion. Delta vs AWS: `unique_together(project,key)` + `update_or_create` overwrites in place — exactly one ciphertext per key, no history, no version_id, no stages. (`vault/models.py:64`; `vault/views.py:128-132`.) Effort: **L**. Pointer: introduce a `SecretVersion` model (immutable, version_id UUID, ciphertext) + a label→version mapping; rework `secret_add` to insert versions.
- **Automatic & scheduled rotation (rotate-now + schedule)** — *missing*. Why it matters: rotation is the flagship value of a managed secrets manager. Delta vs AWS: no rotation hook, no schedule fields, no scheduler (no Celery/cron/management commands), and zero-knowledge means the server can't re-encrypt without the passphrase. Effort: **L**. Pointer: requires versioning + envelope encryption first; then add rotation-config fields on Secret, a `rotate` endpoint, and a Celery-beat/`django-q` scheduler.
- **DeleteSecret with recovery window + RestoreSecret + ForceDelete** — *missing*. Why it matters: accidental deletion of a secret is catastrophic; a recovery window is a standard safety net. Delta vs AWS: deletes are immediate hard `.delete()` with no `deleted_at`/recovery window/restore. (`vault/views.py:140`; `Secret` has no deletion-state fields.) Effort: **M**. Pointer: add `deleted_at`/state fields to Secret, soft-delete default, RestoreSecret + ForceDelete endpoints, and a sweeper management command; exclude soft-deleted from list/read.
- **Write API with idempotency (CreateSecret/PutSecretValue/UpdateSecret + ClientRequestToken)** — *missing*. Why it matters: machines must be able to create/update secrets safely under retries. Delta vs AWS: the programmatic API is GET-only; all mutations require a human session + TOTP via the web UI; no ClientRequestToken/dedup. (`vault/api.py` GET-only; `vault/views.py:128`.) Effort: **M**. Pointer: add POST/PUT handlers in `vault/api.py` + routes in `vault/api_urls.py`; persist tokens with version rows for replay/mismatch semantics.
- **GetSecretValue / BatchGetSecretValue (by id/version/stage)** — *partial*. Why it matters: batch retrieval and version/stage selection are core read ergonomics. Delta vs AWS: single-key read works, but no batch endpoint, no version-id/version-stage selectors (no versioning exists), returns raw ciphertext (zero-knowledge) not decrypted value. (`vault/api.py:34-47`; `vault/api_urls.py:5-8`.) Effort: **M**. Pointer: add a batch endpoint + `?versionId`/`?versionStage` params; depends on versioning.
- **ListSecrets filtering/pagination + DescribeSecret metadata** — *partial*. Why it matters: lists must scale and metadata-without-value is a distinct, frequently-used read. Delta vs AWS: list returns an unbounded flat key array with no pagination/filtering; no DescribeSecret; no metadata fields to describe. (`vault/api.py:23-31`; `settings.py:149-157` has no pagination config.) Effort: **M**. Pointer: add DRF pagination class + filter params in `vault/api.py`; add a `describe` endpoint; surface `created_at`/`updated_at`.
- **Tagging and tag-based access/filtering** — *missing*. Why it matters: organization, cost allocation, and ABAC. Delta vs AWS: no tag storage on Secret/Project, no tag filters, no tag-based authz. Effort: **M**. Pointer: add a JSONField or `SecretTag` model on Secret + tag params on list/create; couples with the policy engine for ABAC.
- **SecretString + SecretBinary payload support** — *missing*. Why it matters: certificates, keystores, and binary credentials are common secret payloads. Delta vs AWS: crypto is hard-bound to UTF-8 str via `.encode()/.decode()`; no type discriminator, no binary/file upload path. (`vault/crypto.py:50-55`; `Secret` has only `key`+`ciphertext`.) Effort: **S**. Pointer: add a `payload_type` field + a base64 binary path in `vault/crypto.py` and the write/read views.
- **GetRandomPassword generator** — *missing*. Why it matters: convenience for seeding rotation and minting strong values. Delta vs AWS: no generator endpoint or UI; values are always user-supplied. Effort: **S**. Pointer: add an endpoint using `secrets.choice` over a configurable alphabet with length/exclude/require-type params; return without persisting.
- **Client-side caching library / SDK** — *missing*. Why it matters: cuts API calls/latency/cost; the local-decryption logic only exists as a docstring today. Delta vs AWS: no shippable SDK, no in-memory TTL cache, no HTTP cache headers. (`vault/api.py` returns ciphertext+KDF only.) Effort: **M**. Pointer: a pip-installable client wrapping the `dhk_` API that does PBKDF2/Fernet locally + an in-memory TTL cache; add `Cache-Control`/`ETag` server-side.
- **Production hardening / operational readiness** — *missing*. Why it matters: the current config is dev-only. Delta vs AWS: `DEBUG=True`, hardcoded `django-insecure-` SECRET_KEY, empty `ALLOWED_HOSTS`, no HSTS/SSL-redirect/secure-cookie settings, no health-check endpoint, no pinned deps, no Dockerfile/deploy tooling, no metrics. (`settings.py:30-35`.) Effort: **M**. Pointer: env-drive SECRET_KEY/DEBUG/ALLOWED_HOSTS, add security middleware settings, a `/healthz` route, `requirements`/lockfile, and a Dockerfile.
- **Cross-region/cross-account replication & multi-node HA** — *missing*. Why it matters: DR and availability for a critical dependency. Delta vs AWS: single Postgres, single app process, in-process session key custody (`SESSION_KEYS`) blocks horizontal scaling. (`settings.py:90-101`; `vault/views.py:8`.) Effort: **L**. Pointer: HA Postgres + DATABASE_ROUTERS, move session keys to a shared store, build a replication/promote path. (See Out-of-scope.)
- **Managed DB-credential rotation integrations (RDS-style)** — *missing*. Why it matters: AWS's marquee managed-rotation feature. Delta vs AWS: no structured/typed secrets, no integration-target model, no rotation logic, and zero-knowledge precludes server-side rotation. Effort: **L**. Pointer: depends on versioning + envelope encryption + scheduler; add a target/integration model. (Largely out-of-scope for a self-hosted clone.)

## Quick wins

- **SecretBinary support** (**S**) — add a `payload_type` discriminator and a base64 path in `vault/crypto.py:50-55`; unlocks certs/keystores with minimal surface change.
- **GetRandomPassword generator** (**S**) — a self-contained `secrets.choice` endpoint with no persistence and no dependency on any other gap.
- **Audit logging** (**M but highest leverage**) — an `AuditLog` model + a handful of write hooks closes the most glaring security gap for a secrets manager and requires no crypto redesign.
- **DeleteSecret recovery window** (**M**) — soft-delete + restore is a high-safety, self-contained change to `Secret` and `vault/views.py:140` that prevents irreversible data loss.
- **List pagination** (**S**) — set `DEFAULT_PAGINATION_CLASS`/`PAGE_SIZE` in `settings.py:149-157`; trivial and prevents an unbounded-response footgun.

## Out-of-scope / acceptable omissions

- **Cross-region/cross-account replication & multi-node HA** — these are properties of AWS being a globally-managed service. A self-hosted clone can reasonably defer this to standard infrastructure (HA Postgres, load-balanced stateless app, DB-level replication) rather than reimplementing AWS's managed replication. The one in-app prerequisite worth doing is moving session key custody off the process (`vault/views.py:8`) so the app can scale horizontally.
- **Managed DB-credential rotation integrations (RDS/Aurora templates)** — deeply AWS-ecosystem-specific (Lambda templates, EventBridge signals, RDS targets). A self-hosted clone can ship generic scheduled rotation hooks instead of provider-specific managed integrations.
- **KMS-backed CloudHSM custom key stores / imported key material** — the *abstraction* (pluggable key provider) is worth building; the specific HSM/custom-key-store features are reasonable to skip for a self-hosted deployment.
- **Console-grade tag policies / SCPs / AWS Organizations governance** — these are org-management features of AWS, not core to a secrets vault; basic tags + ABAC cover the practical need.
- **Pure zero-knowledge retention as-is** — acceptable and even a *differentiator*, but note it is mutually exclusive with server-driven rotation, server-side GetSecretValue, and envelope encryption under a server-held CMK. A clone must consciously choose a parallel server-side-key model for those features rather than treating zero-knowledge as a free addition.
