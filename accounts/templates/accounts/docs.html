Getting started

doctorhide is a Django 6 + DRF zero-knowledge secrets vault. This guide gets you from a clean checkout to your first unlocked project, and walks through the secure first-login flow: sign up, enroll TOTP, and save your one-time backup codes.

1. Install & run

There is no requirements.txt — dependencies are installed inline. Create a virtualenv and install the deps:

uv venv venv
uv pip install --python venv/bin/python django djangorestframework django-otp "qrcode[pil]" "psycopg[binary]" python-dotenv
source venv/bin/activate

Start Postgres. The app expects it on host port 5433 (mapped to the container's 5432):

docker run -d --name doctorhide-postgres \
  -e POSTGRES_DB=doctorhide \
  -e POSTGRES_USER=doctorhide \
  -e POSTGRES_PASSWORD=doctorhide \
  -p 5433:5432 \
  -v doctorhide_pgdata:/var/lib/postgresql/data \
  postgres:17

Copy the example environment file. It already contains the five POSTGRES_* values matching the docker defaults above (host 127.0.0.1, port 5433). Real process env vars take precedence over .env.

cp .env.example .env

Run the migrations, create an admin account, and start the dev server:

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver

The app is now at http://127.0.0.1:8000/. Open that root URL to land on the home page — it does not auto-redirect, so use the nav to reach Sign up.

Note: every route in this project has no trailing slash (e.g. /signup, /login, /totp/enroll, /projects).

2. Sign up

Go to /signup and fill the three fields: username, password1, password2. The form checks that the username is unique (case-insensitive), that the two passwords match, and that the password passes Django's validators.

Important: signing up does not log you in. Your account is unusable until you finish TOTP enrollment. On success you are redirected straight to /totp/enroll.

3. Enroll TOTP with the QR code

At /totp/enroll you'll see a QR code. Scan it with an authenticator app (Google Authenticator, Authy, 1Password, etc.). The QR encodes the device's provisioning URL.

If you can't scan, expand the "Can't scan?" disclosure to copy the manual otpauth:// provisioning URL and enter it by hand.

Then type the current 6-digit code from your authenticator and submit. On a correct code, doctorhide confirms the device, issues your backup codes, logs you in, and redirects to the backup-codes screen. If the code is rejected, re-enter it — a clock-drift hint is shown (make sure your device clock is accurate).

4. SAVE your backup codes — download the PDF

You are now on /totp/backup-codes, which displays your 10 one-time backup codes. Each code works exactly once. These let you log in if you ever lose your authenticator, so store them somewhere safe right now.

⚠️ Do this now: click the "Download PDF" button. This is the single most important step on this screen. It downloads doctorhide-backup-codes.pdf (a application/pdf attachment) containing your username and all 10 codes in a printable layout. The codes are only shown this once — after you leave this screen they cannot be retrieved.

  • The Download PDF button serves the file from route /totp/backup-codes.pdf (it reuses the same session-held codes, so download before navigating away).
  • The Continue button takes you to /projects to start using the vault.

If you click Continue or refresh after the codes leave your session, the PDF link will no longer have anything to serve and redirects you back. So: download (or print) first, then Continue.

5. Returning logins

On later visits, go to /login and enter your username and password. That's only the first factor — you are then sent to /totp/verify to enter your second factor. There you can use either a current 6-digit authenticator code or one of your backup codes (each backup code works once). On success you land on /projects.

The entire vault (projects, secrets, API keys) requires an OTP-verified session, which is exactly what this flow gives you.

Using the web app

This is a hands-on walkthrough of the doctorhide browser UI: creating a project, setting and using its passphrase, adding and deleting secrets, and minting and revoking a project API key. It assumes you are already logged in and OTP-verified (you completed signup, scanned your authenticator, and saved your backup codes). Every vault page requires a verified two-factor session.

One thing to know up front: doctorhide is zero-knowledge. Your project passphrase is never sent to the server in a form that can be stored, and the server keeps only a salt, an iteration count, a verifier, and per-secret ciphertext. If you forget the passphrase, the secrets cannot be recovered. None of the routes in this app use a trailing slash.

1. Create a project and set its passphrase

  1. Go to /projects (the Projects link in the top nav). This lists the projects you own.
  2. Open /projects/new and fill the form. There are two fields:
    • Project name — required, must be unique among your own projects.
    • Salt (the passphrase) — required, at least 8 characters. This is the secret you will type to unlock the project, and it is the only thing that can decrypt your secrets. As the form itself warns: "The salt encrypts this project's secrets. We never store it — if you lose it, the secrets are unrecoverable." Store it somewhere safe.
  3. Click Create project. The server generates a random salt, derives a key from your passphrase (PBKDF2-HMAC-SHA256, 600,000 iterations), stores a verifier, and creates the project. You are redirected to the project detail page at /projects/<public_id> (project ids look like proj_<hex>).

A newly created project is auto-unlocked for the current session, so you can start adding secrets immediately without re-typing the passphrase.

2. Unlock and lock

The project detail page at /projects/<public_id> is either locked or unlocked for your current session.

  • Unlock: when locked, the page shows an Unlock panel ("Enter the salt to view or add secrets."). Type your passphrase into the Salt field and click Unlock. The server re-derives the key from the stored salt and iterations and checks it against the verifier. If correct, the derived key is cached in your session and the page now shows your secrets and API keys. If wrong, you get a "Wrong salt." error and stay locked.
  • Lock: when unlocked, a Lock button appears at the top of the page. Click it to drop the cached key from your session. The secrets and add-secret form disappear and you are back to the Unlock panel. Locking does not delete anything; it just forgets the key until you unlock again.

The cached key lives only in your session while unlocked. Logging out, or the session ending, also effectively re-locks the project.

3. Add and delete secrets

You must have the project unlocked to add a secret (otherwise you get "Unlock the project first.").

  1. Add: in the Secrets panel, fill the two inputs — key (the secret's name, e.g. gmail.com or DATABASE_URL) and value (the secret content) — then click Add. Both are required (otherwise you get "Both key and value are required."). On submit the value is encrypted with the unlocked key and stored only as ciphertext. Adding a secret whose key already exists updates that secret in place.
  2. Reveal: secrets are listed by key only, with the value shown as ••••••••. Values stay hidden until you click the per-row Reveal link, which reloads the detail page with ?reveal=<id> and decrypts just that one secret for display.
  3. Delete: click Delete on a secret's row. It is removed immediately and you stay on the detail page.

4. Mint a project API key (shown only once)

Project API keys let machines read this project's secret names and ciphertext through the REST API under /api/secrets. They are scoped to this one project.

  1. In the API keys panel on the project detail page, click Generate API key.
  2. The page reloads and shows the freshly minted raw key once, in a highlighted box: "New API key — copy it now, it won't be shown again:"

This is the only time the full key is ever shown. The server stores only the key's prefix, a SHA-256 hash of the secret portion, and the last four characters — so it cannot display the full key again. Afterward the list only shows the prefix, last four characters, and usage status. Copy the raw key immediately into your machine's config or secret store. It looks like this:

dhk_<id>_<secret>

Here <id> is a per-key random identifier (not the project's public_id), and the dhk_<id> portion is the stored prefix.

You use it as a bearer token against the project API. There are two endpoints:

  • List secret names: GET /api/secrets returns the key-derivation metadata (project_id, kdf, salt, iterations) plus a keys array of the project's secret names. It does not return any ciphertext.
  • Fetch one ciphertext: GET /api/secrets/<key> returns the same metadata plus key and the encrypted ciphertext for that one secret (or 404 {"detail": "Not found."} if there is no such key). The path accepts slashes in the key.
# list the secret names in the project
curl -H "Authorization: Bearer dhk_<id>_<secret>" \
  https://your-host/api/secrets

# fetch the ciphertext for one secret
curl -H "Authorization: Bearer dhk_<id>_<secret>" \
  https://your-host/api/secrets/gmail.com

The kdf field is returned as the literal string pbkdf2-sha256. The API authorizes fetching ciphertext plus this key-derivation metadata only. It does not grant decryption — a client still needs the project passphrase to derive the key (from salt + iterations) and decrypt locally. The detail page's "Client config" panel shows exactly that metadata and a copy-pasteable single-secret curl example against /api/secrets/<key>.

5. Revoke an API key

The API keys panel lists each key as prefix…last_four with a status of never used, last used <date>, or revoked. To disable a key, click Revoke on its row. The key is marked revoked immediately and stops authenticating against the API. Once revoked, the Revoke button no longer appears for that key and its status reads revoked. Revoking is the right move if a key is leaked or no longer needed — you cannot un-revoke, so just generate a new one when you need a replacement.

Quick reference

  • List projects: /projects
  • Create project: /projects/new (Project name + Salt/passphrase ≥ 8 chars)
  • Project detail / unlock / secrets / keys: /projects/<public_id>
  • Reveal one secret: /projects/<public_id>?reveal=<id>
  • API — list secret names (no ciphertext): GET /api/secrets
  • API — fetch one ciphertext: GET /api/secrets/<key>
  • Auth header: Authorization: Bearer dhk_<id>_<secret> (key shown once)

API reference

doctorhide exposes a tiny, read-only machine API. There are exactly three GET endpoints and no write methods: secrets are created and managed only through the human web UI, never through this API. The base for vault calls is /api/ (no /v1/ prefix), and the introspection probe lives at the project root /whoami. Examples below assume the dev server at http://127.0.0.1:8000.

The API never returns plaintext. It is zero-knowledge: the server only ever stores the per-project salt, iteration count, a verifier, and each secret's Fernet ciphertext. The detail endpoint returns the ciphertext plus the KDF metadata you need to derive the key yourself; your passphrase is never sent to the server and decryption happens entirely on the client.

Authentication

There are two kinds of bearer tokens, used by two different surfaces. Both go in a standard Authorization header with the Bearer keyword.

  • Project keys (dhk_<public_id>_<secret>) authenticate the two /api/secrets endpoints. Mint one in the web UI on a project detail page (Keys → new); the raw token is shown once. The key authorizes fetching ciphertext and metadata only — it does not grant decryption.
  • Service-account keys (dh_live_<public_id>_<secret>) authenticate /whoami. /whoami also accepts a logged-in browser session.

Header shape for the vault endpoints:

Authorization: Bearer dhk_<public_id>_<secret>

Common 401 responses: a header that does not split into exactly two whitespace parts returns {"detail": "Malformed Authorization header."}; a wrong prefix, unknown key, bad secret, or a revoked/expired key returns {"detail": "Invalid API key."}.

GET /api/secrets — list secret names + KDF metadata

Returns the names of every secret in the authenticated project, plus the KDF inputs. No values, no ciphertext.

curl http://127.0.0.1:8000/api/secrets \
  -H "Authorization: Bearer dhk_8f3a2c10b7d49e15_AbCdEf...secret..."

Response:

{
  "project_id": "proj_8f3a2c10b7d49e15",
  "kdf": "pbkdf2-sha256",
  "salt": "Yk9mUXc3c0RqVHZ3dA==",
  "iterations": 600000,
  "keys": ["DATABASE_URL", "gmail.com", "STRIPE_SECRET_KEY"]
}

The salt is standard base64; iterations is per-project (default 600000) — always use the value from the response, not a hardcoded constant.

GET /api/secrets/{key} — fetch one ciphertext + KDF metadata

Returns the same KDF metadata plus the requested secret's name and its Fernet ciphertext. The key path segment uses a <path> converter, so it may contain slashes and dots (for example DATABASE_URL, gmail.com, or app/config.json). There are no query parameters.

curl http://127.0.0.1:8000/api/secrets/DATABASE_URL \
  -H "Authorization: Bearer dhk_8f3a2c10b7d49e15_AbCdEf...secret..."

Response:

{
  "project_id": "proj_8f3a2c10b7d49e15",
  "kdf": "pbkdf2-sha256",
  "salt": "Yk9mUXc3c0RqVHZ3dA==",
  "iterations": 600000,
  "key": "DATABASE_URL",
  "ciphertext": "gAAAAABm...Fernet-token...=="
}

If the key is not in the project you get 404 {"detail": "Not found."}. Note again: the response carries ciphertext, never the decrypted value. The verifier is not returned by the API.

Decrypting locally

Derive the Fernet key from your passphrase plus the response's salt and iterations, then Fernet-decrypt the ciphertext. A wrong passphrase surfaces as InvalidToken when decrypting a real ciphertext (the verifier is not exposed by the API). Watch the base64 asymmetry: the salt is decoded with standard base64, while the derived key is encoded URL-safe.

import base64, requests
from cryptography.fernet import Fernet
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

def derive_key(passphrase, salt_b64, iterations):
    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=base64.b64decode(salt_b64),   # STANDARD base64 for the salt
        iterations=iterations,             # from the response, not hardcoded
    )
    return base64.urlsafe_b64encode(kdf.derive(passphrase.encode()))  # URL-safe -> Fernet key

BASE = "http://127.0.0.1:8000/api"
HEADERS = {"Authorization": "Bearer dhk_8f3a2c10b7d49e15_AbCdEf...secret..."}

r = requests.get(f"{BASE}/secrets/DATABASE_URL", headers=HEADERS).json()
key = derive_key(my_passphrase, r["salt"], r["iterations"])
plaintext = Fernet(key).decrypt(r["ciphertext"].encode()).decode()
# wrong passphrase -> cryptography.fernet.InvalidToken

GET /whoami — identity probe

Reports the resolved principal. Use it to confirm a service-account key is wired up correctly. It works with a dh_live_ key or with a logged-in session; when no Authorization header is present, machine auth is skipped and it falls through to session auth.

curl http://127.0.0.1:8000/whoami \
  -H "Authorization: Bearer dh_live_1a2b3c4d5e6f7a8b_GhIjKl...secret..."

Service-account response:

{"type": "service_account", "name": "ci-deployer"}

Human session response:

{"type": "user", "username": "alice@example.com"}

Decrypting a secret (client-side)

DoctorHide is zero-knowledge: the API only ever hands you ciphertext plus the key-derivation metadata. It never stores or returns your passphrase or any plaintext. Decryption happens entirely on your machine. The flow is:

  1. Fetch the secret with your project API key (Bearer dhk_<key_id>_<secret>). The response includes salt, iterations, and ciphertext.
  2. Re-derive the Fernet key from your passphrase using PBKDF2-HMAC-SHA256 with the returned salt and iterations.
  3. Fernet-decrypt the ciphertext locally.

Two encoding details must match the server exactly, or decryption fails:

  • The salt is standard base64 — decode it with base64.b64decode.
  • The 32 derived bytes are then re-encoded with URL-safe base64 to form the Fernet key.
  • The passphrase is encoded as UTF-8.
  • Always use the iterations value from the response (it is per-project), not a hardcoded constant.

Runnable example. It calls GET /api/secrets/<key>, derives the key, and decrypts:

import base64
import requests
from cryptography.fernet import Fernet, InvalidToken
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC


def derive_key(passphrase: str, salt_b64: str, iterations: int) -> bytes:
    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=base64.b64decode(salt_b64),   # salt is STANDARD base64
        iterations=iterations,             # use the value from the response
    )
    return base64.urlsafe_b64encode(kdf.derive(passphrase.encode()))  # URL-safe -> Fernet key


BASE = "http://127.0.0.1:8000/api"
API_KEY = "dhk_<key_id>_<secret>"
PASSPHRASE = "your-project-passphrase"   # never sent to the server

r = requests.get(
    f"{BASE}/secrets/DATABASE_URL",
    headers={"Authorization": f"Bearer {API_KEY}"},
)
r.raise_for_status()
data = r.json()
# data = {"project_id": "proj_...", "kdf": "pbkdf2-sha256",
#         "salt": ..., "iterations": 600000,
#         "key": "DATABASE_URL", "ciphertext": "gAAAAAB..."}

key = derive_key(PASSPHRASE, data["salt"], data["iterations"])
try:
    plaintext = Fernet(key).decrypt(data["ciphertext"].encode()).decode()
except InvalidToken:
    raise SystemExit("Wrong passphrase (or tampered ciphertext)")

print(plaintext)

A wrong passphrase derives a different key, and Fernet raises cryptography.fernet.InvalidToken — that is how you detect a bad passphrase, since the verifier is not exposed over the REST API.

This example was executed against vault/crypto.py: a secret was encrypted with crypto.encrypt(key, plaintext) using a key from crypto.derive_key(passphrase, salt, iterations), then the client code above decrypted it back to the original plaintext. The key produced by the client derive_key was verified byte-for-byte identical to crypto.derive_key, and a wrong passphrase raised InvalidToken as expected.

The list endpoint returns only the key names (in a keys array) plus the same KDF metadata (no ciphertext). Fetch a specific key to get its ciphertext:

curl -s -H "Authorization: Bearer dhk_<key_id>_<secret>" \
  http://127.0.0.1:8000/api/secrets

curl -s -H "Authorization: Bearer dhk_<key_id>_<secret>" \
  http://127.0.0.1:8000/api/secrets/DATABASE_URL

The <key> path segment uses a path converter, so keys may contain slashes or dots (for example app/config.json or gmail.com). Note there are no trailing slashes anywhere in this API.

Security model

doctorhide is built so that the server can hold your secrets without ever being able to read them. Three things make that true, and all three are enforced in code: encryption happens before data reaches the database, API keys are stored only as hashes, and every account is locked behind TOTP.

Zero-knowledge vault

Each project has a passphrase (the UI labels it "Salt" on the create/unlock forms, but the POST field is named passphrase and it must be at least 8 characters). The passphrase is never sent to or stored by the server in any usable form. From it the server derives an encryption key and throws the key away as soon as the request ends.

Key derivation lives in vault/crypto.py and uses PBKDF2-HMAC-SHA256:

  • Salt: 16 random bytes generated per project, stored as standard base64 (generate_salt()).
  • Iterations: 600000 by default, stored per project as a mutable field (Project.iterations), so it is read back per request rather than hardcoded.
  • Output: 32 raw bytes, then URL-safe base64 encoded into a Fernet key (AES-128-CBC + HMAC-SHA256).

What the server actually persists per project is only: salt, iterations, and a verifier. The verifier is Fernet(key).encrypt(b"doctorhide-verify") — an encrypt-then-MAC token used to check a passphrase on unlock without storing the passphrase. On unlock the server re-derives the key from the submitted passphrase plus the stored salt and iterations, then runs crypto.verify_key; a mismatch throws Fernet's InvalidToken and the UI shows "Wrong salt."

Per secret, the server stores only the ciphertext (a Fernet token). There is no plaintext column and no passphrase column anywhere:

  • Project → salt, iterations, verifier (never the passphrase).
  • Secret → ciphertext (never the plaintext value).

While a project is unlocked in the web UI, the derived Fernet key is held only in the Django session (session["vault_keys"], a map of {public_id: fernet_key_str}). Locking a project (POST /projects/<public_id>/lock) removes that entry, after which secrets cannot be decrypted again until you re-enter the passphrase.

The API never returns plaintext

The two machine endpoints hand back ciphertext plus the KDF metadata you need to derive the key yourself — they never decrypt:

  • GET /api/secrets → project_id, kdf ("pbkdf2-sha256"), salt, iterations, and keys (key names only).
  • GET /api/secrets/<key> → the same metadata plus key and ciphertext.

The verifier is not exposed by the API. A client derives the key locally and decrypts; a wrong passphrase surfaces as a Fernet InvalidToken when decrypting a real secret. Decryption mirrors vault/crypto.py exactly — note the asymmetry: the salt is standard base64, but the derived key must be URL-safe base64:

import base64, requests
from cryptography.fernet import Fernet
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

def derive_key(passphrase, salt_b64, iterations):
    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=base64.b64decode(salt_b64),   # salt: STANDARD base64
        iterations=iterations,             # use the value from the response
    )
    return base64.urlsafe_b64encode(kdf.derive(passphrase.encode()))  # key: URL-SAFE

HEADERS = {"Authorization": "Bearer dhk_<public_id>_<secret>"}
r = requests.get("http://127.0.0.1:8000/api/secrets/DATABASE_URL", headers=HEADERS).json()
key = derive_key(passphrase, r["salt"], r["iterations"])
plaintext = Fernet(key).decrypt(r["ciphertext"].encode()).decode()
# wrong passphrase -> cryptography.fernet.InvalidToken

API keys are hashed and shown once

Project API keys have the form dhk_<public_id>_<secret> (and service-account keys dh_live_<public_id>_<secret>). The server stores only a SHA-256 hash of the secret half; on each request it re-hashes the presented secret and compares with hmac.compare_digest. Because the raw secret is never persisted, it is displayed exactly once:

  • Creating a key (POST /projects/<public_id>/keys/new) stashes the raw token in session["vault_new_api_key"].
  • The project detail page pops it and shows a "copy it now" warning box, then it is gone for good. If you lose it, revoke and mint a new one.

Keys can be revoked (.revoke()), and authentication rejects any key whose revoked_at is set or whose expires_at has passed. Authenticating with a dhk_ key only authorizes fetching ciphertext and KDF metadata — it does not grant decryption, since the passphrase is required and is never on the server.

TOTP is mandatory

A password alone never produces a usable session. Signup creates the account but does not log you in; it sets a half-authenticated marker (session["totp_pending_user_id"]) and forces you through TOTP enrollment first. Login is the same two-step gate: the password step only sets the pending marker, then routes you to verify your second factor.

  • Enrollment confirms a 6-digit TOTP token, then issues 10 one-time backup codes (a django_otp StaticDevice) shown once, with a Download PDF option.
  • Verification uses django_otp match_token, which accepts a TOTP code or a backup code and enforces clock-drift tolerance and replay protection.
  • Every vault view is decorated with @otp_required (not merely @login_required), so an OTP-verified session is required to reach any project, secret, or key — a stolen password cannot open the vault.

Backup codes are single-use; store the PDF somewhere safe, because each code works only once.
